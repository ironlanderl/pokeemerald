# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

Two things live here, and it matters which one you are working on:

1. **An unmodified pret decompilation of Pokémon Emerald.** The acceptance test is byte-exactness: `make compare` must print `pokeemerald.gba: OK`. Any edit to a shared `src/` file is only correct if the ROM is unchanged.
2. **A native Linux port** (`platform/native/`, branch `native-linux-sdl2`) that compiles the game for the host and emulates the GBA's memory-mapped I/O on top of SDL2 + OpenGL. It builds the stock ROM as a *dependency* and consumes its data in place.

Commit messages on the native work follow `native: <lowercase description>`. Upstream commits follow pret's convention (`<subsystem>: <description>`).

## Commands

### ROM build (repo root)

```bash
make                     # matching build (agbcc), the default and the one `compare` applies to
make modern              # build with arm-none-eabi-gcc instead of agbcc
make -j$(nproc)          # parallel build
make compare             # build, then sha1 the ROM against rom.sha1  <-- the correctness test
make syms                # emit pokeemerald.sym
make tools               # build the tools/ helper programs
make clean               # objects, assets, generated sources, tools
```

`make compare` and `make modern` are flags on `make all`, not separate builds (`COMPARE=1`/`MODERN=1`).

`tools/` holds small host programs built on demand: `gbagfx` (graphics → .4bpp/.lz), `preproc` (`INCGFX`/`INCBIN`/charmap expansion), `mapjson`, `jsonproc`, `mid2agb`, `ramscrgen`, `gbafix`, `scaninc`. Assets are generated into `build/assets`; nothing generated is committed.

### Native port

```bash
make -C platform/native            # build (also builds the ROM first, via `make compare`)
make -C platform/native run        # build and launch
make -C platform/native clean
make -C platform/native PROFILE=1              # per-stage frame profiler in timing.c
make -C platform/native EXTRA_CFLAGS=-DPPU_ABLATE_OBJ   # ablation builds
make -C platform/native ARCH=x86_64             # cross build (needs $(ARCH)-linux-gnu-gcc)
```

Host requirements: `libsdl2-dev`, `libglew-dev`, `libelf-dev`, `pkg-config`.

Runtime flags (`--help` for the authoritative list):

```
--rom FILE --save FILE --scale N --frames N --shot FILE.ppm
--audio FILE.wav --press-at FRAME --press BITS --menu
```

`--frames N --shot out.ppm` is the headless capture path; `--press-at/--press` injects `REG_KEYINPUT` bits from a given frame so a capture can drive the game past menus. The debug overlay toggles on **F1** or **Ctrl+Shift+D**.

Keyboard maps onto the GBA's buttons as: Z=A, X=B, Enter=Start, Backspace=Select, S=R, A=L, arrows=D-pad (`video.c:544`).

### Tests

There are none. The decomp has no test suite, and neither does the port. Verification is `make compare` for the ROM side and a visual/headless run for the port side.

### Comparing disassembly

`./asmdiff.sh <start-addr> <length>` disassembles both `baserom.gba` and `pokeemerald.gba` over an address range and diffs them.

## Architecture: the decompilation

- `src/` — ~310 C files, flat, named for the subsystem they implement (`battle_main.c`, `overworld.c`, `pokemon.c`, `pokeball.c`…). `src/data/` holds the data tables: hand-written `.h` tables alongside JSON-derived ones regenerated by `json_data_rules.mk`.
- `include/` mirrors it. `include/constants/` is enormous and is the authoritative source for every numeric constant in the game; prefer adding a constant there over hardcoding a magic number.
- `include/gba/` is the hardware layer: `io_reg.h` (`REG_*` macros), `types.h`, `m4a_internal.h` (sound), `syscall.h` (BIOS calls). This is what a hardware port has to emulate or replace.
- `data/` is preprocessed assembly: scripts, map headers, tilesets, layouts, text. `data/maps/<Name>/` holds each map's JSON-derived sources, assembled into `build/emerald/...` by `map_data_rules.mk`.
- `asm/` and `data/*.s` are still assembly — the decomp is not complete. `constants/*.h` there are used by the assembler.
- `tools/agbcc/` is the matching compiler (dropped in by `agbcc`'s `install.sh`; gitignored). It is not in the repo.
- Linking is driven by `ld_script.ld` with generated fragments: `sym_bss.ld`, `sym_ewram.ld`, `sym_common.ld` (from the `sym_*.txt` files) and `memory.ld` (from `memory.txt`, the EWRAM/IWRAM allocation manifest).

The build pipeline for every `.c` file is: `cpp` → `tools/preproc` (expands `INCGFX`/`INCBIN`, converts text through `charmap.txt`) → `agbcc` → `as`. Matching this exactly is why the port's native build mirrors the same three stages.

## Architecture: the native port

### The core idea

The GBA's address space is emulated by **mapping real host memory at the real GBA addresses** (`memory.c`). EWRAM, IWRAM, IO, palette RAM, VRAM, OAM, flash and the ROM itself are all `mmap`ped into place, so the game's existing `REG_*` and `*(u16 *)VRAM_ADDR` pointer arithmetic keeps working with no changes. The first 64 KiB of the ROM window is mapped writable/private so `RtcInit`'s cart-GPIO write at boot doesn't fault.

### The build pipeline

Four stages, driven by `platform/native/Makefile`:

1. `make -C . compare` — the *unmodified* ROM build. Produces a byte-exact retail ROM plus the ARM ELF, so assets and symbol layout are exactly the originals.
2. `tools/rompatch` — reads the ARM ELF and emits three generated files into `build/native/`:
   - `rom_syms.h` — ROM-resident symbols declared at their true ROM address.
   - `rom_patches.c` — a `{rom_offset, target}` table for every **absolute pointer baked into ROM-resident data**. At startup `memory.c` rewrites each word to the native address of its target, so `gScriptCmdTable` and friends dispatch to natively compiled code.
   - `rom_syms.S` — the same symbols as assembler definitions.
3. Compile all of `src/*.c` for the host (cpp → preproc → cc, mirroring the ROM build's stages) plus the platform layer, with `-DMODERN=1 -DPLATFORM_NATIVE=1`.
4. Link with `native.ld` at **0x40000000** — above the emulated window (0x02000000–0x09000000) so native code cannot collide with it, and below 4 GiB because ROM-resident data stores absolute 32-bit pointers to native symbols.

**Assets are never copied into the native binary.** Graphics, maps and sound data stay in the mapped ROM.

### Files

| File | Role |
|---|---|
| `native.h` | Shared declarations, the memory-map constants, and the platform API. Read this first. |
| `main.c` | Entry point and argument parsing; calls `AgbMain()`. |
| `memory.c` | Host mapping of every GBA region; applies the ROM pointer patches. |
| `timing.c` | Virtual frame clock, scanline counter (`REG_VCOUNT`), interrupt dispatch, IE/IF/IME. |
| `ppu.c` | Background and sprite rasterisation, windows, blending, HBlank DMA. |
| `video.c` | SDL2 window, GL context, keyboard input, and the present thread. |
| `dma.c` | The GBA DMA controllers. |
| `bios.c` / `stubs.c` | BIOS calls; hardware the port does not implement. |
| `mixer.c` / `seq.c` / `pcmout.c` | Native ports of the m4a mixer and sequencer, and the host audio device. |
| `debug_menu.c` / `debug_menu_ui.cpp` | The ImGui overlay (below). |
| `imgui/` | Vendored Dear ImGui v1.92.9b, core plus SDL2 and OpenGL3 backends only. |

### Threading

Three threads, and the split is load-bearing — read `video.c:10-41` before changing anything here.

- **Clock thread** (`timing.c`) owns `VCOUNT` and nothing else. It exists because `m4aSoundInit` busy-waits on VCOUNT during boot, before the game's loop starts. It publishes the scanline and raises `IF`; the game's thread acknowledges it.
- **Game's thread** runs `AgbMain`. Rasterises the frame in the VBlank handler, then calls `native_video_publish_frame()`, which memcpy's into a triple buffer and publishes the index with a release store. It never blocks on the display.
- **Present thread** owns the GL context. Waits for a published frame, uploads it, draws the quad, pumps the overlay, and swaps. The vsync wait happens here, where it costs the game nothing.

Presentation deliberately happens **off the interrupt path**: doing it inside `VBlankIntr` gated the game's frame servicing on the display refresh. The triple buffer (rather than a lock) exists so the game never waits for the presenter and the presenter never reads a frame still being written.

Input is sampled on the game's thread inside the VBlank handler, because `ReadKeys` and one-frame-late presses depend on it.

### Interrupt model

The GBA copies its ARM `IntrMain` dispatcher from ROM into IWRAM and points the IRQ vector at it. The native port dispatches interrupts in C from `timing.c`, so that copy is skipped and `INTR_VECTOR` goes unused (`src/main.c:311`). `WaitForVBlank` advances the virtual clock rather than spinning on a hardware flag.

### The ImGui overlay

Split across two translation units because ImGui is C++ with no `extern "C"` guards while the game's headers are C (`include/sprite.h` uses `template` as an identifier):

- `debug_menu.c` — the C half: a lock-free command queue and read-only probes of live game state. It never writes emulator state directly; the overlay mutates the PPU through the queue.
- `debug_menu_ui.cpp` — the C++ half: drains the queue, builds and draws the panels. The only file that talks to ImGui.

`debug_menu.h` must carry an `extern "C"` guard or the C++ half mangles every name the C half defines. The header is a prerequisite of both objects so an edit invalidates both.

The ImGui OpenGL3 backend is told to use **our** GLEW loader (`IMGUI_IMPL_OPENGL_LOADER_CUSTOM` plus `-include GL/glew.h`) rather than its bundled gl3w — two loaders disagreeing about entry points is how you get a backend that works in isolation and not in the program.

### What is real and what is stubbed

Real: **PPU/VRAM**, **DMA**, **timers/interrupts**, **BIOS**, **flash/save**, **video/input** — all driven through the game's own largely unmodified C. **Sound** is the exception to "unmodified": the m4a mixer and sequencer were re-implemented natively in `mixer.c` / `seq.c` (APU/PSG channels, reverb, key-split, attack/decay envelopes, CGB retrigger), with `src/m4a.c` touched only for pointer narrowing. Note `stubs.c` still allocates `SoundMainRAM[0x800]` as a landing pad, because `m4aSoundInit` copies `src/m4a_1.s`'s ARM body there at boot even though the native mixer replaces it.

Stubbed or dead (`platform/native/stubs.c` and a few `#ifdef`s): **link cable and RFU** (all wireless), **multiboot / BIOS slave download**, **the GameCube handshake**, **RTC**.

Two scope limits worth knowing before you chase a bug in them: the PPU implements **DISPCNT modes 0 and 1 only** (3/4/5, mosaic and OBJ_VRAM1 are deliberately absent — verified unused), and rendering is **scanline-accurate** because battle transitions, the Pokenav and field wipes rewrite scroll and window bounds per scanline via HBlank DMA.

The flash window is a real 128 KiB `MAP_SHARED` mmap of the `.sav` file, so `src/agb_flash.c`'s save state machine runs unmodified. `native_flash_sync()` is a no-op — the kernel persists.

### Keeping `src/` untouched

The port changes only **29 files under `src/` and `include/` (+645/−57), in ~20 `#if` regions**. The design principle throughout is that it keeps the retail code path and intervenes only where (a) an ARM self-relocating trampoline or a 64-bit pointer would break, or (b) an unbounded spin would deadlock. When you need host-specific behaviour, prefer a new function in `platform/native/` reached through the existing hooks over growing the `#ifdef`s in `src/`.

Two categories of guard deserve respect:

- **Don't move the wireless-adapter guard.** `IsWirelessAdapterConnected()` in `src/link.c` returns FALSE early not just as an optimisation — the RFU stub leaves `gSTWIStatus` NULL, and the real path would segfault. The comment in the source says "do NOT move this guard".
- **`stubs.c`'s GameCube latch is not a no-op.** `s_handshake_seen` drives `gcmb_field_2` 1-then-0, because the copyright screen gates on 0→1→2→0. Reporting a constant 1 strands it in `COPYRIGHT_START_FADE`.

The two `-Wno-*-int-cast` flags in the native Makefile cover the benign 32-bit→pointer widenings; the one genuinely dangerous case — a *function* pointer built by casting an integer — was removed (`SetReadFlash1` / `VerifyFlashSector` in `src/agb_flash.c`).

### Save-file layout compatibility

The subtlest thing the port has to get right. On a 64-bit host, host pointers are 8 bytes and struct layout differs, but save-resident and ROM-resident structs **must** keep the cartridge's exact byte layout and 4-byte pointer stride. Three mechanisms handle this:

- **`uptr32`** (`include/gba/types.h`) — a pointer stored as `uint32_t`, with `SAVE_PTR_TO` / `SAVE_PTR_FROM` to widen and narrow. Applied to ROM-resident fields too, because `sound/*.inc` tables are assembled with 4-byte pointer strides and must match on both targets.
- **`GBA_STRUCT_ABI_ALIGN`** — `__attribute__((aligned(4)))`, reproducing agbcc's old-ARM-ABI "round every struct up to 4". On the GBA the macro expands to nothing, so the ROM stays byte-identical.
- **`STATIC_ASSERT`s in `src/save.c`** pin the native layout to the cartridge (`SaveBlock1 == 15752`, `SaveBlock2 == 3884`, `PokemonStorage == 33744`, `Berry2 == 28`, `EnigmaBerry == 52`, plus `offsetof` spot-checks). These are compile-time checks, and the closest thing to a test suite the port has.

If you change a struct in `global.h`, `global.berry.h` or `global.fieldmap.h`, the `STATIC_ASSERT`s will catch it — do not "fix" them by loosening the assertion.

## Conventions

- The port's own files carry a block comment at the top explaining what the file is, why it is structured the way it is, and the non-obvious decisions — especially the bugs that were already hit and fixed. **Match that.** The comments are unusually valuable here because most of them record a specific past failure.
- When you fix something, write down *why it was broken*, not just what changed. That is the established style in `platform/native/` and it is what makes the next debugging session cheaper.
- `make -C platform/native` is the only test the port has. Build it before claiming anything works.

## This machine's environment

Verified 2026-10-05. Check before assuming on a different machine:

- **`make compare` works here** and is the real acceptance test — it prints `pokeemerald.gba: OK`. `tools/agbcc` is installed, and `arm-none-eabi-as` / `-ld` / `-objcopy` are in `/usr/bin`. The non-modern build preprocesses with `$(CC) -E` (host `cc`), so it needs no ARM compiler of its own.
- **`make modern` does *not* work here** — `arm-none-eabi-gcc` and `arm-none-eabi-cpp` are not installed. `DEVKITARM=/opt/devkitpro/devkitARM` is exported in the environment but that directory does not exist (`/opt/devkitpro` has only `devkitA64`). Don't offer a modern build as a way to verify a change here.
- **The library layout is single-prefix (`/usr/lib`), not Debian multiarch.** `/usr/lib/x86_64-linux-gnu` does not exist. Anything hardcoding a Debian path or a `*-linux-gnu` glob fails here, usually *silently*, because `2>/dev/null` in a shell pipeline swallows the error. Ask the toolchain instead: `$(CC) -print-file-name=libc.so.6`, `pkg-config --variable=libdir`. Two such assumptions have already cost debugging time — an empty symbol-exclusion list, and ld's default `SEARCH_DIR` being discarded by `-T native.ld` (which needs `-Wl,-rpath-link`).
- The X display here is not capturable with `import`, so screenshot verification has to go through the port's own `--frames N --shot out.ppm` headless path. That path was previously observed to hang rather than write the PPM — if a capture never appears, suspect that before suspecting the PPU.
